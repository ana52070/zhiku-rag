# 操作进度与 OCR 说明

日期：2026-10-09。

## 操作进度

上传资料、单文件重建和全部索引重建共用全局进度面板，切换管理页面仍能看到。批量上传显示已处理文件数量、当前文件、阶段及已用时间。

- 文件传输：浏览器 XMLHttpRequest 根据实际传输字节显示百分比；传输 100% 仅表示发送完成，还需要服务器解析和索引。
- 解析文档：显示正在处理的文件；无法预先确定耗时，不显示伪造百分比。
- OCR：显示已处理图片数量。图片总数未预先统计，因此使用不定进度条。
- 生成向量：每个成功返回的 embedding 批次更新完成片段数量，单批最多 32 个片段。
- 保存索引：数据库提交完成后才计入已处理文件数。
- 失败：区分处理完毕与处理成功，显示“需检查”，保留错误并提示查看文件列表。上传格式错误、连接失败、索引失败不会报告成功。

总进度按已处理文件数量计算，不代表剩余时间估计。长文件尚未完成时，总进度可能不变，但当前阶段和时间持续显示。批量上传仍逐份处理，未增加服务器并行负载。

进度查询仅允许管理员，原 API Key 权限不变。状态仅存于服务内存，不写入业务数据库；最多保留 200 条，完成状态在后续操作时清理超过一小时的记录。服务重启后进度记录失效；连接中断时应刷新确认文件状态，避免重复上传。进度记录不包含管理员令牌、API Key 或文档原文。

## 当前 VPS 的 OCR

实际检查结果：Tesseract 4.1.1，简体中文 `chi_sim` 与英文 `eng`；另外安装有 `osd`，当前识别参数使用 `chi_sim+eng`。CPU 执行，没有 GPU 或 OCR 云服务。

流程为：原生文字提取 → 扫描 PDF 页面或 Office 内嵌图片 → 本地 Tesseract → 带来源的识别文字 → 分块 → 已配置的 embedding 接口 → 本地 SQLite 索引。

扫描 PDF 使用 pypdfium2 5.13.0 渲染页面，通常为 300 DPI，并设像素上限；Pillow 11.3.0 负责图片方向、尺寸和灰度处理。混合 PDF 保留原生文字，并补充图片 OCR；Word、Excel、PPT 内嵌图片的识别结果记录段落、工作表位置或页码。

单张图片识别最长 30 秒，每份文档最多 200 张图片，OCR 处理总时限 600 秒。引擎串行运行，限制单进程线程数量，避免抢占 VPS 资源。超过限制、无法解码或识别超时会显示需要检查；这不是“全部图片都识别成功”的保证。

图片不上传 OCR 云服务；识别出的文字会发送到管理员配置的 embedding 接口。该接口可能是本地服务，也可能是外部模型服务，取决于当前模型配置。

OCR 只识别文字，不理解图表、产品外观或工程图结构；手写、模糊图片、复杂底纹和业务术语可能识别错误。前次实测“研发部”识别成“研友部”，需要人工核对重要信息。

新上传自动 OCR；已有文件需重建索引后补充 OCR。本次增加进度显示不主动重建业务资料。

后端测试覆盖处理中的进度读取、管理员隔离、重建实际完成数、失败反馈、重复操作标识拒绝、OCR 工作线程进度以及向量批次完成后才更新计数。浏览器测试覆盖批量上传、全部和单文件重建、失败收尾及 320 至 1440 像素布局；现有 Office 预览与管理流程纳入回归。
